# 앱 아키텍처 구조

본 앱은 모바일 클라이언트에서 발생하는 요청을 백엔드 서버가 처리하고,
데이터베이스와 상호작용하는 구조로 설계하였다.

전체적인 구조는 다음과 같다.

[ 모바일 앱 (Client) ]
          │
          │ HTTP Request
          ▼
┌─────────────────────┐
│         API         │
│  요청 수신 및 검증   │
└─────────────────────┘
          │
          ▼
┌─────────────────────┐
│       Service       │
│   비즈니스 로직 처리 │
└─────────────────────┘
          │
          ▼
┌─────────────────────┐
│       Domain        │
│  데이터 규칙 및 속성 │
└─────────────────────┘
          │
          ▼
┌─────────────────────┐
│     Repository      │
│    DB CRUD 처리     │
└─────────────────────┘
          │
          ▼
┌─────────────────────┐
│      Supabase       │
│     데이터베이스     │
└─────────────────────┘


## 1. Client

모바일 앱에서 사용자의 입력을 받아 백엔드 서버에 HTTP 요청을 보내고,
서버로부터 전달받은 결과를 사용자에게 보여주는 계층이다.

사용자는 앱을 통해 경기 선택, 출발 지역 입력, 여행 일정 생성 및 수정,
장소 조회, 리뷰 작성 등의 기능을 이용할 수 있다.

프론트엔드는 JavaScript를 기반으로 개발한다.


## 2. API 계층

API 계층은 모바일 앱에서 전달되는 HTTP 요청을 가장 먼저 처리하는 계층이다.

주요 역할은 다음과 같다.

- 클라이언트의 HTTP 요청 수신
- 요청 데이터의 유효성 검증
- 적절한 Service 호출
- Service의 처리 결과를 클라이언트에 응답

API 계층에서는 핵심적인 비즈니스 로직을 직접 처리하지 않고,
요청을 적절한 Service 계층으로 전달하는 역할에 집중한다.

예를 들어 사용자가 새로운 여행 일정을 생성하면,

Client
  ↓
POST /tour
  ↓
API
  ↓
TourService

와 같은 흐름으로 요청이 전달된다.


## 3. Service 계층

Service 계층은 앱의 핵심적인 비즈니스 로직을 담당한다.

API 계층에서 전달받은 요청을 바탕으로 여러 기능을 조합하여
하나의 업무 흐름(Workflow)을 처리한다.

주요 역할은 다음과 같다.

- 여행 일정 생성 및 수정
- 경기 정보를 기준으로 한 일정 구성
- 장소 추천 및 일정 관리
- 리뷰 작성 및 조회 처리
- Repository를 이용한 데이터 조회 및 저장
- 여러 데이터 간의 관계를 고려한 업무 흐름 조율

예를 들어 여행 일정을 생성하는 경우,

경기 정보 확인
      ↓
사용자 출발 정보 확인
      ↓
주변 장소 정보 조회
      ↓
일정에 장소 추가
      ↓
전체 일정 저장

과 같은 여러 작업을 하나의 업무 흐름으로 조율한다.

따라서 Service 계층은 사용자의 요청을 실제 서비스 기능으로 구현하는
중심적인 계층이다.


## 4. Domain 계층

Domain 계층은 앱에서 사용하는 데이터의 핵심적인 규칙과 속성을 정의한다.

각 데이터가 어떤 정보를 가져야 하는지,
그리고 어떤 상태가 유효한지를 정의하는 역할을 담당한다.

본 앱에서는 다음과 같은 주요 데이터가 Domain의 대상이 된다.

- User
- League
- Tour
- ScheduleDetail
- Place
- Review

예를 들어 Tour는 하나의 원정 경기 여행 일정을 나타내며,
사용자 정보, 관람할 경기, 일정 시작 및 종료 시간, 참여 인원 등의
속성을 가진다.

또한 ScheduleDetail은 전체 일정에 포함되는 개별 방문 일정을 나타내며,
방문 장소와 방문 시간, 일정 상태 등의 정보를 가진다.

Domain 계층을 별도로 구성함으로써 데이터의 구조와 핵심 규칙을
Service나 API의 구현 코드와 분리할 수 있다.


## 5. Repository 계층

Repository 계층은 데이터베이스와 직접적으로 상호작용하는 계층이다.

주요 역할은 데이터의 CRUD(Create, Read, Update, Delete) 처리이다.

Repository에서는 비즈니스 로직을 처리하지 않고,
데이터베이스에 데이터를 저장하거나 조회하는 역할에 집중한다.

예를 들어 UserRepository는 다음과 같은 작업을 담당한다.

- 사용자 생성
- 사용자 조회
- 사용자 정보 수정
- 사용자 삭제

데이터가 필요한 Service는 데이터베이스에 직접 접근하지 않고
Repository를 통해 데이터를 요청한다.

Service
   ↓
UserRepository
   ↓
Supabase

이러한 구조를 통해 데이터베이스 접근 코드와 비즈니스 로직을 분리할 수 있다.


## 6. Database

데이터베이스는 Supabase를 사용한다.

현재 데이터베이스는 다음과 같은 주요 테이블을 중심으로 구성되어 있다.

- User: 사용자 정보 관리
- league: KBO 경기 일정 관리
- Tour: 사용자가 생성한 전체 여행 일정 관리
- schedule_detail: 일정에 포함된 개별 장소 및 방문 시간 관리
- Tour_Place: 관광지 및 장소 정보 관리
- review: 사용자가 작성한 장소 리뷰 관리

각 테이블은 외래 키를 통해 서로 연결되어 있으며,
사용자 → 여행 일정 → 세부 일정 → 장소 및 리뷰와 같은 관계를 구성한다.


## 7. 전체 데이터 처리 흐름

사용자가 앱에서 특정 KBO 원정 경기를 선택하고 여행 일정을 생성하는 경우,
다음과 같은 흐름으로 데이터가 처리된다.

사용자
  │
  │ 경기 및 출발 지역 입력
  ▼
모바일 앱
  │
  │ HTTP Request
  ▼
API
  │
  │ 요청 검증 및 전달
  ▼
Service
  │
  ├── 경기 정보 확인
  ├── 장소 정보 조회
  ├── 일정 구성
  └── 일정 저장 요청
  │
  ▼
Domain
  │
  │ 데이터 구조 및 규칙 적용
  ▼
Repository
  │
  │ CRUD
  ▼
Supabase
  │
  │ 데이터 저장 및 조회
  ▼
Repository
  │
  ▼
Service
  │
  ▼
API
  │
  │ HTTP Response
  ▼
모바일 앱
  │
  ▼
사용자

이와 같이 각 계층이 담당하는 역할을 분리하여,
API는 요청 처리, Service는 비즈니스 로직, Domain은 데이터 규칙,
Repository는 데이터베이스 접근을 담당하도록 구성한다.

이를 통해 각 계층의 책임을 명확하게 하고,
향후 기능 추가나 수정이 발생하더라도 특정 계층의 변경이
다른 계층에 미치는 영향을 최소화할 수 있도록 설계하였다.
